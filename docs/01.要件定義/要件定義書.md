# 要件定義書 - kakeibo（OCI 移行版）

## 1. プロジェクト概要

### 1.1. 目的

現在 Google Apps Script（GAS）と Google スプレッドシートで運用している個人家計簿システムを、
OCI（Oracle Cloud Infrastructure）上で稼働する Web アプリケーションとして再構築する。

### 1.2. 背景

現行システムには以下の課題がある。

- **スプレッドシート依存**: データ量の増加に伴い集計数式が重く、リレーショナルな集計・検索ができない
- **GAS の制約**: 実行時間上限、デバッグ性の低さ、テストの書きづらさ
- **拡張の限界**: 収入・資産残高といった新たな管理対象を追加しづらい
- **AI 判定の不安定さ**: Gemini API によるカテゴリ自動判定が期待どおりに機能しない

### 1.3. 方針

- データストアを Google スプレッドシートからリレーショナルデータベースへ全面移行し、**DB を唯一の正**とする
- スプレッドシートおよび GAS は移行完了後に**完全廃止**する
- Google への依存は **決済通知メールの取得のみ**に縮小する
- AI（Gemini API）によるカテゴリ自動判定は**廃止**する

## 2. 対象範囲

### 2.1. スコープ内

| 分類 | 内容 |
| ---- | ---- |
| 支出管理 | 決済通知メールの自動取込、手動入力、固定費 |
| 収入管理 | 給与・賞与・その他収入の記録（**新規**） |
| 資産管理 | 口座・電子マネー等の残高記録と推移（**新規**） |
| 集計・可視化 | 月次収支、カテゴリ別集計、予算対比、資産推移 |
| マスタ管理 | カテゴリ、店舗ルール、固定費、固定収入、口座、決済手段、利用者 |
| 認証 | Google アカウントによる家族メンバーのログイン |
| 運用 | バックアップ、エラー通知、ログ |

### 2.2. スコープ外

- 金融機関 API・スクレイピングによる残高自動連携（残高は手動記録とする）
- レシート画像の OCR 登録
- AI / 機械学習によるカテゴリ自動分類
- 確定申告・税務計算の支援
- スマートフォンネイティブアプリ（レスポンシブ Web で対応する）
- マルチテナント対応（本システムは単一世帯専用）

### 2.3. 現行機能との差分

| 現行機能 | 移行後の扱い |
| -------- | ------------ |
| メール自動取込（楽天ペイ / 楽天ペイオンライン / 楽天カード） | 継続 |
| 店舗ルールによるカテゴリ判定 | 継続 |
| Gemini API によるカテゴリ判定 | **廃止** |
| 手動入力 Web 画面 | 継続 |
| 固定費マスタからの月次集計参照 | 継続 |
| 月次集計（予算・実績・差額・過去5ヶ月） | 継続 |
| 収入管理 | **新規追加** |
| 資産残高管理 | **新規追加** |
| 共通パスワード認証 | **廃止**（Google アカウント認証へ変更） |

## 3. 用語定義

| 用語 | 定義 |
| ---- | ---- |
| 取引 | 支出または収入の 1 レコード |
| 変動費 | メール取込・手動入力で登録される都度発生の支出 |
| 固定費 | 住宅ローン等、毎月定額で発生する支出。マスタ定義から月次集計に算入する |
| 店舗ルール | 店舗名キーワードとカテゴリの対応定義。取込時のカテゴリ自動判定に使用する |
| 未分類 | 店舗ルールに一致せずカテゴリが確定していない状態 |
| 口座 | 資産残高の記録単位（銀行口座、証券口座、電子マネー、現金など） |

## 4. 機能要件

### 4.1. メール自動取込機能

#### 4.1.1. 取込対象

以下の決済サービスの通知メールを対象とする。

- 楽天ペイ（アプリ決済）
- 楽天ペイ（オンライン決済）
- 楽天カード

#### 4.1.2. 要件

1. 日次で自動実行する。
2. Gmail 上でラベル付けされた決済通知メールを取得対象とする。ラベル付与は Gmail 側のフィルタ機能で行う。
3. メールの発信元と件名からサービスを識別し、対応する解析処理で内容を抽出する。
4. 抽出項目は、利用日・金額・店舗名・決済手段とする。
5. 1 通のメールに複数明細を含む場合（楽天カード等）は、明細ごとに 1 レコードとして登録する。
6. 取込に成功したメールは処理済みと分かる状態にする。
7. 解析に失敗したメールは未処理のまま残し、再実行で再処理できるようにする。
8. サービスを識別できない、または解析に失敗した場合は、対象メールを特定できる情報を含むエラー通知を送信する。
9. 対応サービスの追加が、局所的な追加のみで完結する構造とする。

#### 4.1.3. 重複排除

1. 取込済みのメールを再取込しない。
2. 同一の取引（日付・金額・店舗名・決済手段が一致するもの）を二重登録しない。

### 4.2. カテゴリ判定機能

1. 店舗ルールを参照し、店舗名にキーワードが部分一致するカテゴリを適用する。
2. 比較の前に、店舗名およびキーワードの大文字小文字・全角半角を正規化する。
3. 複数のルールに一致する場合は、定義順で最初に一致したものを採用する。
4. いずれのルールにも一致しない場合は、カテゴリを **未分類** として登録する。
5. Web 画面に未分類の取引一覧を表示し、利用者がカテゴリを割り当てられるようにする。
6. 利用者がカテゴリを割り当てた際、その店舗名をキーワードとして店舗ルールへ自動登録し、
   次回以降は自動判定されるようにする。
7. 自動登録されたキーワードは、後から利用者が編集・削除できるものとする。

> **補足**: 現行システムでは未ヒット時に Gemini API で推論していたが、判定精度が安定しないため廃止する。
> 上記 4〜6 により、初回のみ手動割当が必要となり、2 回目以降は自動判定される。

### 4.3. 手動入力機能

1. メールで自動取得できない支出（現金払い、口座引落等）を Web 画面から登録できる。
2. 入力項目は、日付（必須）、金額（必須）、店舗名・支払先（必須）、カテゴリ、決済手段、メモ（任意）とする。
3. 直近の登録一覧を表示し、内容の修正および削除ができる。
4. 収入についても同様に手動で登録できる（4.5 参照）。
5. スマートフォンのブラウザから支障なく操作できる表示とする。

### 4.4. 固定費管理機能

1. 固定費として、支払先・金額・カテゴリ・決済手段・適用期間・メモを定義できる。
2. 固定費は取引レコードとして複製せず、月次集計時に定義を参照して算入する。
3. 適用期間外の月には算入しない。
4. 金額改定に対応できるよう、同一支払先で期間の異なる複数の定義を保持できるものとする。

### 4.5. 収入管理機能（新規）

1. 収入を取引の一種として記録する。
2. 入力項目は、日付、金額、収入元（勤務先名等）、収入カテゴリ、入金先口座、メモとする。
3. 収入カテゴリとして、給与・賞与・臨時収入・その他などを定義できる。
4. 毎月定額の収入（給与等）を固定収入として定義し、固定費と同様に月次集計へ算入できるものとする。
5. 月次集計において、収入合計・支出合計・収支差額を算出する。

### 4.6. 資産残高管理機能（新規）

1. 資産の記録単位となる口座を管理する。属性は、口座名・種別（銀行 / 証券 / 電子マネー / 現金 / その他）・
   通貨・表示順・有効フラグとする。
2. 各口座の残高を、基準日を指定して手動で記録する。
3. 同一口座・同一基準日の記録は 1 件に限定し、再登録時は上書きする。
4. 最新の記録日時点における総資産額および口座種別ごとの内訳を表示する。
5. 月次の総資産推移をグラフで表示する。
6. 金融機関との自動連携は行わない。

### 4.7. 集計・可視化機能

1. 月を指定して、以下を表示する。
   1. カテゴリ別の支出実績（変動費 + 固定費）
   2. カテゴリ別の月次予算および予算との差額
   3. 収入合計・支出合計・収支差額
2. カテゴリごとに月次予算を設定できる。予算超過は視覚的に判別できる表示とする。
3. 振替・返金など集計に含めない取引を、集計対象から除外できるものとする。
4. 以下のグラフを表示する。
   1. 月次支出推移（直近 12 ヶ月）
   2. 当月のカテゴリ別支出構成比
   3. 月次収支推移（収入・支出・差額）
   4. 総資産推移
5. 取引一覧を、期間・カテゴリ・決済手段・金額範囲・店舗名で絞り込み検索できる。
6. 取引一覧を CSV 形式で出力できる。

### 4.8. マスタ管理機能

以下のマスタを画面から保守できる。マスタ保守は管理者権限の利用者のみが行える。

- カテゴリ（支出 / 収入の区分、月次予算、集計対象の要否を含む）
- 店舗ルール
- 固定費
- 固定収入
- 口座
- 決済手段
- 利用者（ログインを許可するアカウント）

### 4.9. 認証・認可機能

1. Google アカウントによるログインを提供する。
2. 事前に登録した利用者のみログインを許可し、それ以外はアクセスを拒否する。
3. 未認証状態では、ログイン画面を除く全ページへのアクセスを拒否する。
4. 権限区分を以下の 2 段階とする。
   1. **管理者**: 全機能およびマスタ保守を利用できる
   2. **一般**: 取引の登録・参照・集計閲覧のみ利用でき、マスタ保守は行えない
5. 取引レコードには登録者を記録し、誰が登録したかを追跡できるようにする。
6. セッションには有効期限を設け、一定時間の無操作で再認証を求める。

### 4.10. データ移行機能

1. 現行スプレッドシートの生データ・店舗ルール・固定費マスタ・カテゴリを新システムへ移行する。
2. 移行は一括投入方式とし、繰り返し実行できる形で提供する。
3. 移行後、件数および月次合計金額が移行前と一致することを検証する。
4. 移行完了後、スプレッドシートは参照専用のアーカイブとして凍結し、GAS のトリガーおよびデプロイを停止・削除する。

## 5. 管理対象データ

システムが管理する情報の単位を以下に定める。具体的なテーブル構造は基本設計で定義する。

| 情報 | 概要 | 主な発生源 |
| ---- | ---- | ---------- |
| 取引 | 支出・収入の明細 | メール取込 / 手動入力 |
| カテゴリ | 支出・収入の分類 | マスタ |
| 店舗ルール | 店舗名からカテゴリを判定する規則 | マスタ / 自動学習 |
| 固定費 | 毎月定額で発生する支出の定義 | マスタ |
| 固定収入 | 毎月定額で発生する収入の定義 | マスタ |
| 口座 | 資産の記録単位 | マスタ |
| 残高記録 | 口座ごと・基準日ごとの残高 | 手動入力 |
| 決済手段 | 支払方法の分類 | マスタ |
| 利用者 | ログインを許可するアカウントと権限 | マスタ |
| 取込ログ | メール取込の実行結果 | バッチ |

### 5.1. データに関する業務ルール

1. 取引データは物理削除せず、履歴を保持する。
2. 金額は円単位の整数として扱い、小数を発生させない。
3. 日付・時刻は日本時間（`Asia/Tokyo`）を基準とする。
4. 過去 10 年分の取引データを保持できること。

## 6. 非機能要件

### 6.1. 可用性

1. 単一ノード構成のため、インスタンス障害時は全機能が停止することを許容する。
2. 目標復旧時間（RTO）は 1 営業日以内とする。
3. 目標復旧時点（RPO）は 24 時間以内とする。

### 6.2. 性能

1. 主要画面の応答時間は、通常のデータ量において 2 秒以内を目標とする。
2. メール取込処理は、日次の対象件数（数十件程度）を 5 分以内に処理する。
3. 10 年分（数万件規模）の取引データを保持しても、集計画面の応答性能を維持する。

### 6.3. セキュリティ

1. 認証情報・API キー等の機密情報を、ソースコードおよびコンテナイメージに埋め込まない。
   秘密情報管理サービスで管理する。
2. 外部公開は HTTPS のみとし、HTTP はリダイレクトする。TLS 証明書は自動更新する。
3. CSRF・XSS・SQL インジェクションに対する対策を講じる。
4. 本番環境でデバッグ情報を外部に出力しない。
5. マスタ保守機能は管理者権限の利用者のみアクセスできるものとする。
6. データベースを外部ネットワークへ公開しない。

### 6.4. バックアップ・リストア

前提基盤（`infra-oci-ansible`）の要件定義では「インスタンス内のデータの永続化管理は行わず、
紛失を許容する」方針が示されているが、**本システムの家計簿データは決済通知メールからの
再取得が不可能な資産であるため、本システム固有の要件としてバックアップを必須とする。**

1. 日次でデータベースのバックアップを取得し、インスタンス外のストレージへ退避する。
2. 世代管理を行い、日次 30 世代および月次 12 世代を保持する。
3. 四半期に 1 回を目安に、バックアップからのリストア手順を実際に検証する。
4. バックアップの成否を通知し、失敗時に検知できるようにする。
5. バックアップに要するストレージ費用は無料枠内に収めること。

### 6.5. 運用・保守

1. 以下の事象発生時に管理者へ通知する。
   1. メール取込の解析失敗
   2. バッチの異常終了
   3. バックアップの失敗
2. アプリケーションログを収集・参照できるものとする。
3. デプロイを自動化し、手動でのファイル配置を伴わない。
4. データベーススキーマの変更を管理でき、手動での直接変更を必要としない。

### 6.6. コスト

1. OCI の Always Free 枠内での運用を基本とし、恒常的な課金が発生しないこと。
2. 有料の外部 SaaS・API に依存しないこと。

### 6.7. 移植性・保守性

1. ローカル開発環境を構築でき、本番と同一のミドルウェア構成で開発できるものとする。
2. 主要なビジネスロジック（メール解析、カテゴリ判定、集計）に自動テストを整備する。
3. 対応する決済サービスの追加が、局所的な変更で済む構造とする。

## 7. 制約・前提条件

### 7.1. 採用が決定済みの技術

以下は要件定義時点で決定済みの制約とする。個別のライブラリ選定およびバージョンは基本設計で確定する。

| 項目 | 決定内容 | 理由 |
| ---- | -------- | ---- |
| 実行基盤 | 既存の OCI インスタンス上に構築済みの Kubernetes クラスタ | 既存のポートフォリオ基盤を流用する |
| データベース | 既存インスタンス上の MySQL | 構築済みであり、追加コストが発生しない |
| 言語 | Python | 本業（インフラ自動化）で使用する言語とのスキル統合を図る |
| フレームワーク | Django | 管理画面・認証・ORM・マイグレーションを標準搭載し、開発工数を抑えられる |
| 認証基盤 | Google アカウント（OpenID Connect） | 家族が既に保有しており、パスワード運用が不要 |
| メール取得 | Gmail API | 決済通知メールが Gmail に届くため |

### 7.2. その他の前提

1. 本システムは単一世帯・少人数（数名）での利用を前提とし、同時アクセス数は極めて少ない。
2. データベースは既存の MySQL を共用し、本システム専用のスキーマとユーザーを作成する。
3. 外部公開用のドメイン名を用意し、DNS を OCI インスタンスへ向けること。
4. Google Cloud プロジェクトを作成し、Gmail API の有効化と OAuth クライアントの発行を行うこと。
5. 取引の計上は**発生主義**（利用日基準）とし、資産残高は手動記録による実残高とする。

### 7.3. 前提基盤に関する補足

本システムが載る Kubernetes は OCI のマネージドサービス（OKE）ではなく、
kubeadm で構築したセルフマネージドのシングルノードクラスタである。
第 6.1 節の可用性要件は当該構成を前提としている。
