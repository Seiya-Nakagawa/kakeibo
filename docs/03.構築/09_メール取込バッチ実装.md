## 1. 概要

対応Issue: [#24](https://github.com/Seiya-Nakagawa/kakeibo/issues/24)

Gmail APIから決済通知メールを取得し、取引として登録する管理コマンドを実装する。
サービス識別・重複排除・ラベル付け替えを行う。
対応する設計書: [基本設計書3.1節](../02.設計/基本設計書.md#31-メール自動取込要件-41)、
[6.1節](../02.設計/基本設計書.md#61-gmail-api)

**注意**: `kakeibo/mail_import.py`の各サービスの本文解析用正規表現は、実際の決済通知
メールのサンプルで検証できていない暫定実装である（Rakuten系サービスで一般的に知られている
書式を基にしたもの）。運用開始前に実メールで必ず動作確認し、`_ITEM_PATTERN`のラベル
パターンを実際の書式に合わせて調整すること。

## 2. 前提条件

- [08_通知機能実装.md](08_通知機能実装.md) の完了により`build_gmail_service`・
  `notify_admin`が利用可能であること
- Gmail APIの認証情報（`GMAIL_API_CLIENT_ID`等）が設定済みであること

## 3. 手順

### 3.1. Gmailのラベル・フィルタを設定する

[基本設計書3.1.2節](../02.設計/基本設計書.md#312-gmailラベル運用)のとおり、
通知メール送信元アカウントのGmailで以下を設定する。

1. ラベル「`家計簿/未処理`」「`家計簿/処理済`」を作成する
2. 対応する決済通知メール（送信元・件名は[3.1.1節](../02.設計/基本設計書.md#311-サービス識別ルール)を参照）に
   「`家計簿/未処理`」ラベルを自動付与するフィルタを作成する

### 3.2. 環境変数を設定する

`webapp/.env.example`の末尾に以下を追記する。

```dotenv
# メール取込バッチで登録する取引の登録者（基本設計書6.2節）
```

`webapp/.env`に、登録者として扱う利用者（[03_認証機能実装.md](03_認証機能実装.md)で

### 3.4. メール解析ロジックを実装する

`webapp/kakeibo/mail_import.py`を新規作成する。

```python
"""決済通知メールの解析（基本設計書3.1節）。"""

import base64
import hashlib
import re
from dataclasses import dataclass
from datetime import date


@dataclass(frozen=True)
class ServiceRule:
    """サービス識別ルール（基本設計書3.1.1節）。"""

    service: str
    sender: str
    subject_contains: str
    payment_method_name: str


# 対応サービスの追加は、この一覧への行追加のみで完結する（要件4.1.2.9）。
SERVICE_RULES = [
    ServiceRule(
        service="楽天ペイ（アプリ決済）",
        sender="no-reply@pay.rakuten.co.jp",
        subject_contains="楽天ペイアプリご利用内容",
        payment_method_name="楽天ペイ",
    ),
    ServiceRule(
        service="楽天ペイ（オンライン決済）",
        sender="payment@checkout.rakuten.co.jp",
        subject_contains="楽天ペイ（オンライン決済）",
        payment_method_name="楽天ペイ(オンライン)",
    ),
    ServiceRule(
        service="楽天ペイ（注文受付）",
        sender="order@checkout.rakuten.co.jp",
        subject_contains="楽天ペイ 注文受付",
        payment_method_name="楽天ペイ(オンライン)",
    ),
    ServiceRule(
        service="楽天カード",
        sender="info@mail.rakuten-card.co.jp",
        subject_contains="カード利用のお知らせ",
        payment_method_name="楽天カード",
    ),
]


def identify_service(sender: str, subject: str) -> ServiceRule | None:
    """送信元アドレスと件名からサービスを識別する（基本設計書3.1.1節）。"""
    for rule in SERVICE_RULES:
        if rule.sender in sender and rule.subject_contains in subject:
            return rule
    return None


@dataclass(frozen=True)
class ParsedItem:
    transaction_date: date
    amount: int
    counterpart: str


_DATE_LABELS = r"(?:ご)?利用日時?|注文日"
_STORE_LABELS = r"(?:ご)?利用先|(?:ご)?利用店舗|加盟店名"
_AMOUNT_LABELS = r"(?:ご)?利用金額|お支払い?金額"

_ITEM_PATTERN = re.compile(
    rf"(?:{_DATE_LABELS})[:：]\s*(?P<date>\d{{4}}[/年]\d{{1,2}}[/月]\d{{1,2}})日?"
    rf"(?:\s*\d{{1,2}}[:：]\d{{2}})?"
    rf".*?(?:{_STORE_LABELS})[:：]\s*(?P<store>[^\r\n]+?)\s*[\r\n]"
    rf".*?(?:{_AMOUNT_LABELS})[:：]\s*(?P<amount>[\d,]+)円",
    re.DOTALL,
)


def parse_mail_body(body: str) -> list[ParsedItem]:
    """メール本文から取引明細を抽出する（複数明細対応、要件4.1.2.5）。"""
    items = []
    for match in _ITEM_PATTERN.finditer(body):
        year, month, day = re.split(r"[/年]", match.group("date"))
        items.append(
            ParsedItem(
                transaction_date=date(int(year), int(month), int(day)),
                amount=int(match.group("amount").replace(",", "")),
                counterpart=match.group("store").strip(),
            )
        )
    return items


def extract_plain_text(payload: dict) -> str:
    """Gmail APIのmessage.payloadからtext/plain本文を抽出する。"""
    if payload.get("mimeType") == "text/plain":
        data = payload.get("body", {}).get("data")
        if data:
            return _decode_base64url(data)
    for part in payload.get("parts", []) or []:
        text = extract_plain_text(part)
        if text:
            return text
    return ""


def _decode_base64url(data: str) -> str:
    padded = data + "=" * (-len(data) % 4)
    return base64.urlsafe_b64decode(padded).decode("utf-8", errors="replace")


def compute_dedup_hash(
    transaction_date: date, amount: int, counterpart: str, payment_method_name: str
) -> str:
    """取引単位の重複排除用ハッシュ（基本設計書3.1.3節）。"""
    raw = f"{transaction_date.isoformat()}|{amount}|{counterpart}|{payment_method_name}"
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()


def header_value(payload: dict, name: str) -> str:
    for header in payload.get("headers", []) or []:
        if header.get("name", "").lower() == name.lower():
            return header.get("value", "")
    return ""
```

### 3.5. 管理コマンドを実装する

`webapp/kakeibo/management/commands/import_transactions_from_mail.py`を新規作成する。

- ラベル「`家計簿/未処理`」配下のメッセージを列挙し、メッセージごとに以下を行う
  1. 送信元・件名からサービスを識別できない場合は`EmailImportLog`にFAILEDを記録し、
     ラベルはそのまま（次回再処理）とする
  2. 本文を解析できない（明細が0件）場合も同様にFAILEDを記録する
  3. サービスに対応する`PaymentMethod`マスタが未登録の場合もFAILEDを記録する
     （マスタはAdminで事前登録する運用とし、バッチ側では自動作成しない）
  4. 明細ごとに`compute_dedup_hash`で重複排除（既存の取引と同一ハッシュなら
     スキップ）した上で`Transaction`を作成する。`category`は
     `categorization.match_category`で判定する
  5. 成功したメッセージはラベルを「`家計簿/処理済`」へ付け替え、
     `EmailImportLog`にSUCCESSを記録する（`gmail_message_id`はUNIQUEのため
     `update_or_create`で同一行を更新する）
- 識別・解析等に失敗したメッセージがあれば、まとめて`notify_admin`で通知する
  （要件4.1.2.8）
- コマンド全体が例外で終了した場合も`notify_admin`で通知したうえで
  `CommandError`を送出し、CronJobが失敗として扱えるようにする

### 3.6. 設計書にcreated_byの扱いを追記する

[基本設計書6.2節](../02.設計/基本設計書.md#62-バッチの起動方式)に、メール取込で
登録する取引の`created_by`は環境変数`MAIL_IMPORT_USER_EMAIL`で指定した利用者とする旨を
追記する。

### 3.7. テストを追加する

`webapp/kakeibo/tests/test_mail_import.py`（解析ロジック単体）と
`webapp/kakeibo/tests/test_import_transactions_from_mail.py`（管理コマンド、Gmail APIを
フェイクオブジェクトで模擬）に以下を追加する。

- サービス識別・複数明細の解析（楽天カード）が正しく行われること
- 成功時に取引が作成されラベルが付け替えられること
- サービス未識別・解析失敗・決済手段マスタ未登録がそれぞれFAILEDとして記録され、
  `notify_admin`が呼ばれること
- 重複するdedup_hashの明細は取引を作成しないが、メッセージ自体は処理済みとなること
- ラベル未整備・`MAIL_IMPORT_USER_EMAIL`未設定の場合に`CommandError`となり通知されること
